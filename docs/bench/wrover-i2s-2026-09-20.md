# WROVER I2S isolation — 2026-09-20

Hardware: ESP32-WROVER, 8 MB PSRAM (4 MB mapped), TAS5805M at I2C address
`0x2d`. Application address: `192.168.11.241`; Music Assistant:
`192.168.11.132:8927`. UART adapter has RX/TX only: DTR/RTS are not connected.
Enter download mode manually with BOOT/EN; reboot manually with EN.

## MCUboot observation

The application connects to Music Assistant and configures 44.1 kHz stereo.
Previously only `Audio process failed rc=-3 state=3` was visible. A sink error
observer now records the underlying operation, driver error and submitted-block
count in the board's web log without depending on UART output:

```text
[5372 ms] Output request: 44100 Hz channels=2
[5375 ms] Stream: 44100 Hz 16-bit 2 ch
[5395 ms] I2S allocate TX block failed: driver rc=-11 submitted=4
[5395 ms] Audio process failed rc=-3 state=3
```

Four blocks were accepted by `i2s_write`, and START succeeded. The next slab
allocation timed out after 20 ms. No buffer became available in that interval.
This locates the immediate failure in TX completion/buffer return, not an I2C
probe failure. The lower-level cause remains unconfirmed.

UART captured ROM/bootloader messages and PSRAM memory-test success, but not
application diagnostics. Read `/logs` for the sink observer output.

## Direct-boot comparison

Built `build-wrover-sendspin` from the same application source. Added
`CONFIG_REBOOT=y` to the base app configuration because `main` references
`sys_reboot` even when the OTA stub is selected; otherwise direct boot failed
to link. Flashed and hash-verified:

```sh
build-deps/venv/bin/esptool --chip esp32 \
  --port /dev/serial/by-id/usb-1a86_USB_Serial-if00-port0 \
  --baud 460800 --before no-reset --after no-reset \
  write-flash 0x1000 build-wrover-sendspin/zephyr/zephyr.bin
```

UART confirmed `ESP Simple boot` and PSRAM test success. Wi-Fi/Sendspin connected
in about five seconds. The user confirmed audible playback. Web telemetry:

```text
[81468 ms] Stopped: source frames=102486, underruns=0
[81468 ms] Output request: 44100 Hz channels=2
[85345 ms] Sendspin chunks=248 written=170810 dropped=0 underruns=0 sync=1 lat_ms=1435 level=21306 flags=3 rx=136925 B/s vol=62 mute=0 fault=0
[90345 ms] Sendspin chunks=448 written=391210 dropped=0 underruns=0 sync=1 lat_ms=1437 level=21162 flags=3 rx=176973 B/s vol=62 mute=0 fault=0
```

The board is left on the working direct-boot image; OTA is unavailable in this
image. Restoring MCUboot requires flashing its bootloader at `0x1000` and a
signed application at `0x20000` (direct boot overlaps those regions).

This comparison establishes a working hardware/PSRAM/amplifier baseline. It
implicates differences between the MCUboot and direct-boot configurations or
startup paths, but does not yet identify a particular bootloader defect. Next:
compare peripheral-clock, DMA and interrupt initialization with matched configs.

## Track-change stall (fixed)

Switching tracks manually left silence until stop/resume. The logs showed the
old stream reaching `Input EOF`, then `Stream start failed rc=-2` (`EAF_STATE`),
then the old I2S stream timing out reclaiming drained buffers. Two causes:

1. The next `stream/start` tried to configure while the previous stream was still
   draining or pending EOF, so the output owner rejected it.
2. In the pinned ESP32 driver, `I2S_TRIGGER_DROP` clears the active DMA-block
   pointer without returning it to the slab. Repeated cancellations can leave too
   few blocks for a later drain.

Fix: `eaf_board_output_replace` cancels the previous stream, joins its worker and
retires DMA before configuring a fresh reservoir; the sink releases its unsubmitted
block and drains queued DMA before DROP, retaining state if that fails. Covered
by `test_board_output` restart loops and a Zephyr smoke case that requires drain
before DROP while a producer holds an uncommitted block.

## Software validation

- Both WROVER builds compile with the sink error observer.
- Zephyr native-simulation I2S smoke reports `EAF smoke PASS (0)`.
- Native-simulation Clang diagnostics pass. The Xtensa compilation database is
  not supported by the installed host Clang flags; it reports unsupported
  `-mlongcalls`, `-fno-printf-return-value`, and `-fstrict-volatile-bitfields`.
  Use the native-simulation database for HAL Clang checks and the Xtensa GCC
  build for board compilation.
